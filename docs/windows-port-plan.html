1. About this document

This document gives the plan to port Glasscode from macOS to Windows.

The text obeys the writing rules of ASD-STE100. The sentences are short. Each instruction has one command.

File names, command names, and software names are technical names. They stay the same as in the source code.

These words have one meaning in this document:

WordMeaning
ApplicationThe desktop program in crates/glasscode.
Core libraryThe library in crates/glasscode_core. It has no user interface.
DaemonThe server program glasscoded in crates/glasscoded. It operates on Linux.
AgentThe official claude or codex command line program.
SessionOne agent or one shell in one terminal of the application.
GPUIThe user interface toolkit from the Zed project. A frozen copy is in vendor/.
ConPTYThe Windows interface for a pseudo terminal.

2. Summary

Glasscode is a Rust application of approximately 48,500 lines in three crates. At this time, only a macOS build is possible.

The port is possible without a new design. Most of the logic does not use the operating system directly. The work is in three groups:

  • Toolkit. The copy of GPUI in vendor/ contains only the macOS platform. The Windows platform crate is not there.
  • Operating system interfaces. The code uses Unix sockets, file locks, the C time functions, and file modes. Windows does not have these interfaces in the same form.
  • macOS programs and conventions. The code starts programs such as security, open, afplay, lsof, and zsh. It also uses the Command key, the application bundle, and a disk image for delivery.

The plan has nine phases. Phases 0 to 5 give an application that can do local sessions on Windows. Phases 6 to 8 add the server functions, the browser, and the installer.

  • Phase 0Preparation
  • Phase 1Core library
  • Phase 2GPUI on Windows
  • Phase 3Sessions and terminal
  • Phase 4The glasscode command
  • Phase 5Desktop behavior
  • Phase 6Server and telephone
  • Phase 7Browser and voice
  • Phase 8Installer and release

Note

The macOS build must continue to operate during the full port. Each change keeps the macOS behavior the same.

4. Results of the examination

4.1 Method

  1. We read the documents in README.md, docs/, vendor/README.md, and vendor/CHANGES.md.
  2. We read all Cargo manifests and the build scripts in script/.
  3. We searched the three crates for platform conditions, Unix interfaces, external programs, fixed paths, key names, and macOS words.
  4. We did two compile tests on Windows 11 with the Rust toolchain 1.98.1 from rust-toolchain.toml.

Caution

Item R9 is a security defect on Windows. Correct it before the first test build goes to a person.

The file /dev/urandom does not exist on Windows. Then control_ui.rs makes the session secret from the time and the process number. In pair_ui.rs, the pairing token becomes all zeros.

4.5 Parts that need no change

  • The models and parsers in the core library: board, day (after B4), chat, transcript, prompt, markdown, linear, github_tickets, autofix, naming, model, store.
  • All calls to git and gh. Git for Windows and GitHub CLI have the same commands.
  • The terminal emulation. The crate alacritty_terminal has a ConPTY back end.
  • The fonts and icons in crates/glasscode/assets. The program includes them at compile time.
  • The release signature check in update.rs. It uses the ring crate.
  • The data folder. paths.rs uses the home folder, and GLASSCODE_HOME can replace it.

5. Design decisions

IDSubjectDecisionReason
D1Source structureOne source tree for macOS and Windows. Add the module glasscode_core::sys with unix.rs and windows.rs.Platform conditions stay in one place.
D2ToolkitAdd gpui_windows from Zed commit c403bc6. Do not move to a newer GPUI.The frozen copy stays consistent. The macOS build does not change.
D3Data folderKeep %USERPROFILE%\.glasscode.The server uses the same layout. The agents also use folders below the home folder.
D4Control channelA named pipe: \\.\pipe\glasscode-control-<user>. Only the same user can open it. Keep the request files as the second path.Windows gives the process number of the client. The Rust standard library has no Unix socket on Windows.
D5ProgramsTwo programs: the window program and a console program glasscode.exe. The console program has the modes cli, browser-mcp, and relay-connect.A window program cannot write to a console. Agents read the output of the command.
D6Search pathThe application adds the folder of glasscode.exe to PATH of each session.The command operates in PowerShell, cmd.exe, and Git Bash without a script.
D7Claude hooksOn Windows, the hook command is glasscode hook. The status line command is glasscode statusline. Claude gets the settings from a file.The commands do not depend on a shell language. A file prevents quotation problems.
D8Default shellPowerShell 7 if it is installed. If not, Windows PowerShell. A setting lets the user select Git Bash.All Windows computers have PowerShell.
D9Keyssecondary- for the application: Cmd on macOS, Ctrl on Windows. In the terminal, copy and paste are Ctrl+Shift+C and Ctrl+Shift+V.Ctrl+C must go to the program in the terminal.
D10SecretsWindows Credential Manager, through the windows crate.It is the Windows equivalent of the Keychain.
D11ProcessesOne function, sys::command, starts all external programs.It finds .cmd files and hides the console window.
D12Minimum systemWindows 10 version 1809, 64-bit x86. ARM64 comes later.ConPTY starts with this version.
D13ServerThe daemon stays on Linux. WSL is not in the scope.The server design does not change.

6. Work phases

Phase 0. Preparation

  1. 0.1Install the Visual Studio Build Tools with the C++ tools and the Windows SDK.
  2. 0.2Install Git for Windows, GitHub CLI, Node.js, Claude Code, and Codex on the test computer.
  3. 0.3Make the branch windows-port from main.
  4. 0.4Add the module glasscode_core::sys. Put all new platform code in this module.
  5. 0.5Add sys::command. On Windows, it uses PATHEXT and sets CREATE_NO_WINDOW.
  6. 0.6Replace each Command::new in the application and the core library with sys::command.
  7. 0.7Make the daemon crate build only on Unix. On Windows, its main function prints one message.
  8. 0.8Add an automatic build job for Windows and macOS. It does cargo check and the core tests.

Complete when: the macOS build and the macOS tests give the same results as before.

Phase 1. Core library

  1. 1.1Move the socket code of control.rs into sys. Write the named pipe client for Windows.
  2. 1.2Get the process number of the pipe client with GetNamedPipeClientProcessId.
  3. 1.3Use the request files when the pipe gives “access denied”. This is the same rule as on macOS.
  4. 1.4Replace flock in net.rs with std::fs::File::lock.
  5. 1.5Replace localtime_r in day.rs and usage.rs with chrono::Local.
  6. 1.6Replace ps and lsof with the sysinfo crate.
  7. 1.7Write the Credential Manager functions for keychain.rs. Keep the three function names.
  8. 1.8Change resolve_program to use split_paths and PATHEXT.
  9. 1.9On Windows, make login_shell_env return the environment of the process without the removed variables.
  10. 1.10Start curl.exe by name in net.rs.
  11. 1.11Get the computer name from COMPUTERNAME in mirror.rs.
  12. 1.12Make net::random_token public. Add a function for random bytes. Remove all use of /dev/urandom.
  13. 1.13Add windows to this_os in update.rs.
  14. 1.14Do the core tests on Windows. Correct the tests that use Unix paths.

Complete when: cargo test -p glasscode_core -- --test-threads=1 has no failures on Windows and on macOS.

Phase 2. GPUI on Windows

  1. 2.1Get the Zed source at commit c403bc6af644cd0ab60c90045ac6dc3436218809.
  2. 2.2Copy crates/gpui_windows into vendor/gpui_windows. Include the license file.
  3. 2.3Copy all crates that gpui_windows uses and that are not in vendor/.
  4. 2.4Put the Windows sections back into the manifests of gpui, gpui_platform, gpui_util, and http_client. Start with the which dependency of gpui_util.
  5. 2.5Add the new crates to the workspace. Add the necessary features to the windows dependency.
  6. 2.6Change the features font-kit and runtime_shaders of gpui_platform. They must not refer to gpui_macos on Windows.
  7. 2.7Update Cargo.lock. Make sure that the macOS dependencies keep their versions.
  8. 2.8Put the update code of update_ui.rs behind a platform condition.
  9. 2.9Add long path support to gpui.manifest.xml. Worktree paths can be longer than 260 characters.
  10. 2.10Write each change into vendor/CHANGES.md and vendor/README.md.

Complete when: cargo run shows the main window on Windows 11. Text, icons, and the five font families are correct at 100% and 150% scale.

Phase 3. Sessions and terminal

  1. 3.1Set escape_args to true in tty::Options on Windows. Make sure that arguments with spaces stay as one argument.
  2. 3.2Start shell sessions with PowerShell. Do not send the argument -l.
  3. 3.3Write the Claude settings to a file for each session. Give the file path to --settings.
  4. 3.4Add the sub-commands hook and statusline to the console program. They do the work of the two shell commands.
  5. 3.5Start a Claude session. Make sure that the events file gets the four hook events.
  6. 3.6Start a Codex session. Make sure that Glasscode finds the conversation from the cwd field.

  10. 3.10Change the path text for pasted files. Use quotation marks on Windows.
  11. 3.11Start install commands and version commands with cmd.exe /C. Change the example text from brew to winget.
  12. 3.12Do the seven steps of the compatibility list in docs/architecture.md on Windows.

Complete when: a Claude session, a Codex session, and a shell session start, show their activity, and resume after a restart of the application.

Phase 4. The glasscode command

  1. 4.1Add a second program to the application crate for the console. The installer names it glasscode.exe.
  2. 4.2Move the modes cli, browser-mcp, and relay-connect to the console program on Windows.
  3. 4.3Set the window subsystem for the window program in release builds.
  4. 4.4Write the named pipe listener in sys. Use it in control_ui.rs.
  5. 4.5Make the pipe open only for the user of the application.
  6. 4.6Add the folder of the console program to PATH of each session.
  7. 4.7On Windows, do not write the launcher script. Write the plugin folder as before.
  8. 4.8Do a test of the request files from a Codex session with its sandbox on.

Phase 5. Desktop behavior

  1. 5.1Replace cmd- with secondary- in the bindings of the application, the text fields, and the chat view.
  2. 5.2In the terminal on Windows, bind copy, paste, and clear to Ctrl+Shift+C, Ctrl+Shift+V, and Ctrl+Shift+L.
  3. 5.3In the terminal on Windows, send application shortcuts with Ctrl to the program. Examine terminal/keys.rs line 10.
  4. 5.4Add one function that gives the label of a shortcut. It gives ⌘N on macOS and Ctrl+N on Windows.
  5. 5.5Draw the minimize, maximize, and close buttons in the title bar on Windows. Mark the drag area.
  6. 5.6Remove the left space of 84 pixels on Windows.
  7. 5.7Make sure that Ctrl+Q and Alt+F4 stop the application. Windows does not show the macOS menu.
  8. 5.8Show notifications at the bottom right on Windows. Play a Windows system sound.
  9. 5.9Add sys::open_path, sys::reveal_path, and sys::open_url. Use them in place of open.
  10. 5.10Change the system fonts to Segoe UI, Cascadia Mono, and Georgia on Windows.
  11. 5.11Add one function for platform words. Replace “this Mac”, “Finder”, “Keychain”, and “macOS” in all text.
  12. 5.12Do a test of paste and drop for text, files, and images.
  13. 5.13Do a test of the Auto theme with the light and dark modes of Windows.

Complete when: a person can do all local work with the keyboard and the mouse, and no text refers to macOS.

  2. 8.2Write script/bundle-windows.ps1. It builds the release and collects the files.

Sequence

Phase 1 and phase 2 do not depend on each other. Two persons can do them at the same time.

Phases 3, 4, and 5 depend on phases 1 and 2. Phases 6, 7, and 8 depend on phase 4.

The first release for test users is possible after phase 5.

9. Acceptance tests

Do these tests on a clean Windows 11 computer and on a Windows 10 computer.

  1. Install Glasscode. Start it from the Start menu.
  2. Add a project that is a git repository.
  3. Start a Claude session on a new worktree. Send a prompt. Make sure that the activity changes to “working” and then to “idle”.
  4. Start a Codex session. Send a prompt. Make sure that the chat view shows the reply.
  5. Start a shell session. Start git status.
  6. Change a session between the chat view and the terminal view.
  7. Paste an image into a Claude session. Make sure that Claude reads the file.
  8. Stop Glasscode. Start it again. Make sure that each session resumes its conversation.
  9. Hand a Claude session to Codex, and a Codex session to Claude.
  10. Start glasscode board add "Test" in a session. Make sure that the Today board shows the task.
  11. Start a command that needs approval. Approve it in the notification.
  12. Open a pull request in the Git tab. Make sure that the checks and the comments show.
  13. Connect Linear with a key. Stop and start Glasscode. Make sure that the key is still there.
  14. Remove a worktree while a program operates in it. Make sure that Glasscode shows a warning.
  15. Use two accounts of the same agent. Make sure that each stays signed in.
  16. After phase 6: move a session to the server and back.

Q3Which installer and which certificate do we use?An installer for one user, and an organization code signing certificate.
Q4Is PowerShell the correct default shell?Yes, with a setting for Git Bash.
Q5Is a build for Windows on ARM64 necessary?Not in release 1.
Q6Does the Windows work go into the same repository and the same branch?Yes. Use the branch windows-port and merge each phase into main.
