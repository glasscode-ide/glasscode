1. About this document

This document divides the Windows port into 19 vertical slices. One subagent does one slice in one worktree.

A vertical slice gives one complete function that a person or a test can see on Windows. It includes the core code, the user interface code, and the tests for that function.

Each slice ends with one pull request into the branch windows-port. The branch main does not change until the port is complete.

The parent document, GC-WIN-001, gives the reasons and the findings. The finding numbers (B1, R9) and the decision numbers (D4) in this document refer to it.

4. Rules for all slices

  1. Keep macOS the same. Put Windows code behind #[cfg(windows)] or in sys/windows.rs. Do not change macOS behavior unless the slice tells you to.
  2. Use the platform module. Operating system code goes into glasscode_core::sys. Other modules call it. Do not add new cfg conditions in user interface files when a sys function can do the work.
  3. Stay in the slice. Change only the files in the “Files” list of the slice. If a different file must change, write the reason in the pull request.
  4. Do not change vendor/. Only slice S02 can change it. Other slices tell the main agent when they find a defect there.
  5. Do not merge Cargo.lock by hand. When it has a conflict, take the version of windows-port. Then do cargo check to update it.
  6. Start external programs with sys::command after slice S03. Do not use std::process::Command::new directly.
  7. Add tests. Each slice lists the tests. Tests for Windows have #[cfg(windows)]. Tests for the two platforms have no condition.
  8. Obey the code style. Read CONTRIBUTING.md. Comments tell the reason, not the action. Do cargo fmt only on the lines that you changed. The source uses long lines.
  9. Do not put secrets or personal data in code, tests, or pull requests.
  10. Verify before the report. Do each command in the “Verify” list of the slice. Put the real output in the pull request.
  11. Tell the truth in the report. If a step is not complete or a test fails, write that in the pull request.

5. Procedure for the main agent

5.1 Before the first slice

  1. Get the answers of the owner to the questions in section 12.
  2. Make the branch: git switch -c windows-port main, then git push -u origin windows-port. Get the approval of the owner before the push.
  3. Commit the two plan documents in docs/ to windows-port. Subagents read them from their worktree.
  4. Make the folder W:\personal-code\glasscode\wt.

5.2 For each slice

  1. Make sure that all slices in “Depends on” are merged into origin/windows-port.
  2. Make the worktree and the branch with the commands in section 3.
  3. Start one subagent with the Agent tool. Set model to opus. Use the brief in section 6. Do not use the isolation option, because the worktree exists.
  4. Start the other slices of the same wave in the same message, to a maximum of three.
  5. When a subagent gives its report, read the diff: gh pr diff <number>. Do not rely on the report only.
  6. Make sure that the diff obeys section 4 and stays in the “Files” list.
  7. Wait for the two build jobs: gh pr checks <number> --watch.
  8. If the review finds a defect, send the finding to the same subagent with SendMessage. Do not correct it yourself.
  9. Give the owner the “Demonstration” steps of the slice. Wait for the result.
  10. After the approval of the owner, merge with squash. Remove the worktree and the branch.
  11. Tell each subagent that is in work to rebase: git fetch origin, then git rebase origin/windows-port.
  12. Update the status in section 7 of this document and in the heading of the slice. Use a pull request of documents only.

5.3 When two slices of one wave touch the same file

  1. Merge the smaller pull request first.
  2. Tell the other subagent to rebase and to do its “Verify” list again.
  3. If the conflict is not simple, stop the second slice and start it again from the new branch head.
